# 考察 tips

詰まったら上から順に。「→」の先を自分に聞く。

## 読んだ直後

- 自明に見える → 制約の一文を読み落としていないか
- 「解が存在するように入力が選ばれる」 → 解なし判定は不要。構造が緩い
- 端数・実数が許される → 貪欲でよい合図。整数なら NP 困難のことが多い
- 「条件を満たすものを1つ」 → 構築。考えずに実験へ
- 状態が時間で変わる → 各状態の**始まりと終わりを両方**書く。
  終わりが空欄なら永続。from then on / 以後ずっと は飛ばしやすい

## 手が止まったとき

- 良い性質が見えない → **実は状態数が少ないのでは？**
- 構築問題 → 小さいケースの答えを全部並べる。1つではなく全部
- 未知の定数・係数がある → 全探索の答えに合わせて決める
- 候補が多すぎる → 鳩の巣。どれか1つは必ず残らないか
- 候補が絞れた → そこで得た情報を全部使ったか。値だけでなく位置も
- 効く制約が1〜2本 → 貪欲。交換レート（コスト ÷ 消費する資源）の順
- 答えに上限がある → その上限で打ち切れないか
- 2つの量が単調 → 片方を反転して向きを揃えられないか

## 期待値・確率

- 絶対値 / min / max が出た → 期待値の外に出せない
- 「○○を固定すると」 → その状況が起きる確率を掛けたか
- 整数の格子 + 連続の揺らぎ → 距離 0 のときだけ別扱い

## インタラクティブ

- 実数が返ってくる → **0 と比較しない**。真の値のギャップを
  計算して、その 1/10 くらいを閾値にする
- 整数座標しか指定できない → 斜めに引けば実質的に小数位置を
  探れる。接するケースが消えて境界が綺麗に切れる
- max / min にまとめられて返る → 他の成分はノイズ。1つだけ
  振るなら、**他は端ではなく中央に固定**してノイズ床を下げる
- クエリ上限がある → 実際に数える。上限ちょうどは危ない

## 重い・通らない

- オーダーは足りているのに遅い → 情報を落としている
- アクセスが 10^8 超 → 連続かランダムか。連続 10^9/秒、ランダム 10^8/秒
- 内側がランダムアクセス → 連続にできないか
- キーで引いている → 配列の添字にできないか
- メモリが足りない → **次元を使い回せないか**。dp[i][j][k] の i は
  2 枚で足りることが多い
- まだ足りない → 型を落とす / グローバル生配列 / フラット化

## 出す前

- 置いた定数の根拠を1行で言えるか
- 最悪ケースを自分で作って測ったか
- デバッグ出力を消したか
